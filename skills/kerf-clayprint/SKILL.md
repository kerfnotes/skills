# Clayprint

把文字稿整理成簡報或 HTML 報告，也能為既有檔案的指定圖表或圖片換樣式；以原稿和原檔為內容依據。

## 先分流

先辨認內容可否重組，再選交付用途。沿用使用者已給的讀者背景、目的與格式；只有缺口會實質改變取捨時，才詢問一次。

- **只換樣式**：沿用原文，依 [既有檔案流程](references/formats.md)在副本上修改指定圖表或圖片，保留原檔、頁序、公式與可編輯內容。Office 擷取僅是可讀內容與快取，不是整份文件的往返重建模型；讀不到與只取得快取的部分須揭露。
- **內容可重組**：使用者指定的格式優先；沒指定時，依讀者怎麼拿到、怎麼讀這份成品來選：
  - 有人上台講：現場簡報（`present`），依下方〈簡報流程〉。
  - 會前寄出、讀者自己逐頁比較證據：閱讀型簡報，在 `story.json` 根層填 `"mode": "read"`，要說的話寫在頁面上而不是 `notes`；依〈簡報流程〉及[閱讀型簡報](references/layouts.md#閱讀型簡報)。
  - 在螢幕上連續讀或轉寄，或看不出會有人上台講：依 [報告流程](references/report.md)製作 `"layout": "web"` 的 HTML 網頁；要列印或 PDF 時才用預設版型並印 PDF。
  - 只需一張圖：依 [圖表選單](references/charts.md)選圖，以該頁指令交付獨立 SVG 和可重產的圖表 JSON。保留已知單位、期間、來源與影響判讀的限制。

所有交付先依[全交付字級索引](design/README.md#全交付字級索引)選用途、單位與預設來源；既有檔案只套用授權指定目標。

## 原則

1. 觀點在前，證據在後。
2. 一頁一個清楚的判斷：標題 `claim` 寫結論，主題放頁首小字 `kicker`。
3. 先寫結論，再選讓結論一眼可見的圖或版型：效果第一。選單沒有能直接畫出主張的圖時，先把它畫成 SVG 放進輸出資料夾，以[自畫圖](references/charts.md#自畫圖)寫進 `story.json`（`evidence` 頁 `"visual": {"figure": "檔名.svg"}`）或 `report.json`（`figure` 元件），交付時提醒這是選單外的新圖；表格留給讀者要逐格查值的證據。
4. 放不下先修版型、合理重排或拆頁，保留該頁的原稿數字與限制，不逐頁縮字級；閱讀型簡報整份採閱讀預設。
5. `claim` 點名的數字與項目要在當頁可見，強調項目要與主張一致。
6. 依讀者的先備知識安排解釋，簡報與報告都適用；只換樣式時沿用原文。
   - 讀者不熟主題：以白話說清結論，用熟悉的情境或具體例子說明用途與運作；必要術語在首次出現時就地解釋，每頁／節回答一個主要問題。讀者熟悉主題：直接聚焦證據與取捨。
   - 比喻有助理解才用，角色對應須一致；自行設計的例子標為「示意情境」，比喻須明示（如「可以想成……」），可放正文但不作事實證據、不補造數字或因果。
   - 影響判斷的限制放同頁／節正文。
   - 交付前檢查：依已知背景與文中解釋，讀者能否說明結論及其理由；斷點補在首次需要理解之處。

每個版型都有對應的主張；原稿無法支持時就換版型，未決事項用沒有 `tag`／`focus` 的 `list` 或 `columns`。各版型的主張、欄位與容量見 [版型說明](references/layouts.md)。

常見骨架是工具箱，不是必填清單：

- 決策型：封面 → 主管摘要 → 現況／需求 → 證據 → 診斷或方案 → 決議事項；無數字時，封面後以帶 `focus` 的 `statement` 開場。每張證據頁都要被摘要或決議採用，孤立頁刪去。
- 說明型：封面 → 重點摘要 → 拆解 → 流程或時程 → 下一步。

## 資料底線

- 不編造數字；沒有可畫的數字就不放圖表。無日期的流程用 `process`，不捏造月份。
- 畫面上的順序、期限、負責人與原因取自原稿；推論寫在 `notes`。
- 整份主張、封面、摘要與每頁標題不能比原稿說得更強：範圍不說窄也不說滿（如把「最明顯」寫成「只有」、「多數」寫成「都」），不只取原句的一半而丟掉轉折或但書，也不寫出原稿沒有的關係（因果、回應、對立）。標題放不下時刪細節，不改強度。
- 0 是觀察值。論證需要或讀者會預期看到的數字，若原稿未提供，在原位標「未提供」，並列入當頁來源列；若只是版面有那一格，而原稿沒提，就整格省略。缺值輸入與各圖處理方式見 [版型說明](references/layouts.md)和[圖表選單](references/charts.md)。
- 每頁填 `sources.source`；單位、期間只填已知內容。虛構稿註明「虛構示意資料」。
- 推導值是原稿沒寫、自己算出的數字，也包括標題或正文用文字寫的倍數與比例（如「幾倍」「過半」）。算法與原始數字放當頁 `notes`，報告寫在同一節；比值用文字交代分子與分母，不寫成「計算：」算式。驗收器不掃中文數字，這類說法要自己核對。需要觀眾看見時寫 `sources.more`。`sources.more` 會上投影片，`notes` 不會；格式見 [驗收說明](evals/README.md)。

## 簡報流程

以下指令從 skill 根目錄執行；需要 Node 22.7.0 以上。首次安裝、Node 版本不足或缺少套件時，先依 [agent 安裝指引](docs/install.md)完成安裝與驗證。先建立 `out/`，輸出統一放在此處；`script.md` 換成本次原稿。此流程適用於內容可重組的簡報；只換樣式走既有檔案流程。

1. 讀文字稿，確認聽眾及其先備知識、目的、可用數字、來源與資料缺口，依原則 6 決定解釋深度。使用者說明的背景優先；聽眾或目的不明且會改變取捨時，先問一次。
2. 選合適的骨架，寫故事線和每頁一句結論。
   - 原稿是報告、文章、資料或會議紀錄等素材，使用者沒指定要講哪一點：先挑一個讀者在意、原稿本身答得出來的問題，答案就是整份的主張；只留推進這個答案的頁面，其餘不放。答案須是原稿寫出的；要靠原稿沒給的原因或結論才答得出的問題，就換一題。
   - 原稿是已定稿的講稿或大綱：內容照用，不刪減。
   - 使用者已經說了要看什麼：範圍照他說的，不另外選題，也不因此刪減；報告流程也一樣。
3. 依 [版型說明](references/layouts.md)挑支撐結論的版型，並依 [圖表選單](references/charts.md)主動判斷是否適合用圖。
4. 寫 `out/story.json`，每張內容頁在 `notes` 放 1～3 句講稿（要說的話、補充細節），計算另列；影響判斷的限制依原則 6 放在頁面上；閱讀型簡報改把講稿寫在頁面上。執行 `node evals/check.mjs out/story.json script.md` 核對；範例：`node evals/check.mjs examples/story.json evals/fixtures/example-script.md`。
5. 執行 `node scripts/pptx.js out/story.json out/deck.pptx` 建檔。
6. 依 [預覽與交付](references/layouts.md#預覽與交付)執行 `node scripts/preview.js out/deck.pptx out/preview`；輸出 `page-N.png`、`sheet.png`（整份概覽）、`deck.pdf`。0 項容量警告只代表未偵測到溢出，仍逐頁找孤字與不均勻換行。
7. 依警告和預覽修正最弱的一頁，再重建、重驗。能派 subagent 時，可請不同 subagent 對照原稿與需求，分別檢查數字、版面和敘事（含標題是否比原稿強），再整合修正。交付集中列：核心判斷、第 2 步有選題時選定的問題與未放入的原稿內容、缺資料／未完成頁、最弱頁修改前後及原因、哪些圖為原生可編輯／SVG，再依〈交付證據〉分列四層結果。編輯限制見 [設計差異](docs/design-diff.md)。

## 交付證據

簡報、報告與既有檔案都分列四層結果，寫明完成、未驗或受阻及其依據：

1. **程式核對**：生成、原稿數字對照、容量與警告；通過不代表完整事實查核或實際可讀。
2. **實際預覽**：列出軟體、觀看條件與已查看的頁面；檢查遮擋、換行、來源及同頁／同節限制。現場版記錄顯示尺寸與觀看距離，閱讀版檢查 A4 縮印，HTML 檢查窄螢幕，PDF 檢查圖說與來源小字。未實測的項目標未驗。
3. **PowerPoint 原生圖表編輯**：實際開檔改一個原生圖數值才算完成；SVG、XML 或預覽不證明能編輯。不適用的產物註明不適用。
4. **讀者理解**：記錄目標讀者能否說明結論、理由與重要限制；沒有目標讀者回饋時，只回報內容檢視及尚未驗證理解。

檢查（含 subagent）之後又改過的頁或節，交付前要再對照原稿查一次；先前派過 subagent 就交回同一類檢查。交付說明列出這些頁、由誰複查及結果。

外部程式不可用時保留已完成產物，列明受阻原因與未驗項目。密度警告先查該頁內容在原稿已有的理由、定義或限制是否漏寫，再評估併頁、元件拆分或重排；內容完整且留白有助閱讀時記錄理由，維持既有警告，不以補造或重複內容消除提示。量測差異見[簡報填滿](references/layouts.md#填滿與頁數)及 [PDF 警告](references/report.md#警告)。

## 設計層與驗證

預設 clay 設計層；切換 B′ 深藍範例與檢查自訂配色見 [設計層說明](design/README.md)。逐頁檢查判斷、數字、單位、期間、來源、缺值、遮擋與閱讀順序；也查每張圖比較的是否為同類、可比較的項目，以及同一組數字有沒有在相鄰的段落、圖與表重複。驗收器不判斷這些語意問題。

## 套用到既有檔案

先讀 [格式與保留原則](references/formats.md)，在副本上只換目標圖表或圖片。
Office 檔可用 `node scripts/extract.js 原檔 out.json` 擷取文字、表格與可讀的圖表快取。
交付時說明修改範圍、數據來源、讀不到的部分與實際預覽方式。

# 視覺化與作戰圖指引

依 [SKILL.md 第 5 節](../SKILL.md#5-權力地圖) 交圖、補交或更新圖時讀取這份指引，以 [board-template.html](board-template.html) 為底；交付狀態與驗收依同一節，已讀且仍適用時沿用。本檔第 1 節的骨架與三本書的問題每張策略圖都必須具備（完整圖是主結構面板加「其他看法」，精簡圖是三行）。

## 1. 版型：固定骨架，中間照卡點畫

作戰圖要帶出證據支持的判斷，不是把使用者的計畫畫成流程，也不是把正文搬進框框。由上到下：判斷標題 → 轉折點 → 圖例 → 主結構面板（一到兩塊）→ 其他看法。三本書的問題（誰點頭才算數、拍板的人看到什麼、各方在意什麼與退路）每張圖都要答到；哪一個畫成完整面板，看哪一個承載本案的判斷，不是每本書都要一塊。沒有證據的格寫「未知」或「本案尚無法辨認」，空白與未知照實呈現也算正確使用框架。每格一句短語（約 20 字內），長說明留在正文。

1. **判斷標題：** SKILL 第 3 節第一句的前半——這局卡在哪，確定程度跟著證據走，未知照實寫「還不知道」，不改名成「缺口」「還沒落地」。不讀證據就寫得出的標題只是重述計畫，要重寫。
2. **轉折點（緊接標題）：** 第一句的後半，也就是第一步——要改變的那條線、那個人或那一項，以及對誰提出什麼請求或核對什麼，與正文推薦一致。手機上使用者捲第一屏就要看到它。
3. **圖例：** 只列圖中真的用到的線型與標籤；使用者自己說的事不貼標籤，圖例寫明「現況未標來源＝依你描述；推測、未知另標」；標「已核對」要實際讀過文件，且文件內容支持該項敘述，否則仍算依你描述。線型三種：實線箭頭＝已發生、虛線箭頭＝建議你做、點線箭頭＝不知道有沒有這條路；證據標籤用文字（已核對／推測／未知），不只靠顏色。

**主結構：** 挑承載本案判斷的一到兩種畫成完整面板。下面四種最常見，各附適用的卡點；都不合時，照同樣的證據規則畫最能說清卡點的結構。

4. **逐項對照（卡在一份文件、提案或制度改動的內容時）：** 一列一項，欄位「項目｜碰到誰的利益或面子｜拍板的人會怎麼讀｜怎麼處理」。只列會改變結果的項目；誰在意、拍板者怎麼讀，沒證據就標推測。處理欄寫使用者能做的事，與正文一致。
5. **傳遞路線《Power》（卡在拍板者看到什麼：功勞、能見度、資訊被過濾時）：** 一條箭頭一列（人 → 動詞與對象 → 人），帶日期、數字或原話錨點；至少一列已發生、一列擬議（第一步）。拍板者實際看到的與實際經過不一致的地方，就是這塊的對照。「不知道拍板者有沒有收到」畫成點線問句，不畫成「已斷線」。
6. **決策圈《獨裁者手冊》（卡在誰點頭才算數時）：** 針對本輪第一步要處理的那一項決定（不是整個組織；權責不同的另一項決定，例如記功與考績，在框外寫一行，不疊進同一個批准圈），用由外到內的同心框，圈名用白話並保留書中層次：名義上能參與的人（形式參與）→ 誰的話有份量（影響者）→ 少了誰推不動（必要支持／執行）→ 誰能批准或擋下（批准／否決）。只被告知的人留在《Power》連線，不放進決策圈。只畫有依據的圈；沒依據的圈可合成框外一行「待查：角色名稱＋未知」，保留必要支持與核心聯盟的區別，只對會改變下一步的未知附查法；批准或擋下那圈一定畫，未知就寫「還不知道 → 怎麼查」。人物放進哪一圈要有依據；職級、熟識或當場表態都不等於核決權或核心支持。放圈是推測時，標籤標在放圈的判斷上、不標在已知身分上（「Amy（你的直屬主管）：少了她推不動，依據…〔推測〕」）；已知身分放在人名後的括號，推定的權限另寫一句短語並帶〔推測〕，這一格可以超過 20 字，使用者說過的身分仍是已知。拍板者靠誰坐穩（書中的核心致勝聯盟）和「少了誰推不動」不同：只在拍板者自己的位置會影響這項決定時（例如新主管剛上任）才寫成框外一行，無證據寫「還不知道」，否則不寫。查法以第一步要找的那個人為先；可能被轉知的管道（HR、別的主管）照實提醒，不設成開口前提。
7. **利益與退路《Getting to Yes》（卡在交換條件、談不成怎麼辦時）：** 兩欄小標「各方在意什麼」「談不成時你能做的」。關鍵人各一行顧慮或利益（推測要標推測），寫在承擔它的人名下；談不成時分三行白話：自己就能做的（BATNA，沒有就寫「目前沒有」）、還要別人點頭的、還沒到手的機會（使用者提過才寫，沒提寫「你沒提」）。

**其他看法：** 主結構沒有回答到的書問題，各寫一行，開頭寫書名；推測、未知在行內標字。沒畫成面板的《Getting to Yes》那行，至少寫到自己就能做的退路（沒有就寫「目前沒有」）。

**精簡圖（使用者限定字數時）：** 圖內文字也算進使用者的字數上限。只保留判斷標題、轉折點，以及三個看法各一行（《獨裁者手冊》誰拍板或權限未知／《Power》拍板者看到什麼、缺了什麼／《Getting to Yes》對方顧慮與你的退路），使用者原本要的結果（例如考績怎麼認列）至少出現在其中一行；全圖約 120 字內；沿用 board-template.html 的 CSS，用 `.turn` 加一個 `.panel` 內三行 `<li>`（每行開頭寫書名）組成，不放圖例；因為沒有圖例，推測、未知照樣在格內標字（只用〔推測〕〔未知〕），誰有權決定什麼使用者沒說時也要標；和正文合計仍不超過上限，超出時先刪正文裡的重述，不刪標字或使用者要的結果。正文不再重複這三行。

**形式：** 以 [board-template.html](board-template.html) 為底，只留用到的面板，改文字與列數；桌面與手機共用同一份，同一批人物名稱貫穿各塊。兩人局或局部問題只畫相關關係，不為湊版面虛構人物；人物多時優先 4–6 位關鍵人，必要執行者不可省略。判斷建立在數字上（金額影響、工時、版本增量），或使用者要月會簡報等成品時，改用已安裝的簡報／圖表 skill 製作，本圖只保留關係與判斷。

**呈現與交付順序：**
- 環境有 `html_preview`／`html_render` 時：寫一份自含 HTML（內嵌 CSS／SVG，沿用環境主題變數，不覆寫 `:root` 配色、不設整頁背景），先以 `width=375` 預覽並實際看截圖，修到無截斷、重疊與水平溢出，再用 `html_render` 放進回覆。
- 只有 Markdown 的環境：照同樣順序改用 Markdown——判斷標題一行、轉折點一行引言，主結構用對應的表格（逐項對照「項目｜碰到誰｜拍板的人怎麼讀｜怎麼處理」；傳遞路線「誰 → 做了什麼 → 誰｜已發生／建議你做／不知道有沒有｜標籤」；決策圈「圈層｜人與依據｜標籤」；利益與退路「人｜在意什麼｜標籤」＋「談不成時你能做的」一行：自己就能做／還要別人點頭／還沒到手），其他看法各一行，用一句白話說明這裡只能用表格呈現、沒有畫成圖。Markdown 表格在手機與純文字環境都讀得到；Mermaid 只在使用者明說要流程圖且環境支援時用於《Power》那塊。
- 使用者追問「給我看圖」時，直接在當前回覆呈現已驗收且仍適用的圖並指出主線；有新資訊時更新受影響部分並重驗，不只回「前面畫過了」。
- **獨立交付檔案只在明確要求時建立：** 使用者要求完整報告、可下載或離線 HTML 作戰圖時才建立並保留（不依賴 Python、固定 JSON schema 或外部網路資源）。為了預覽而寫的臨時檔不算交付物；使用者明說「不建檔」時一律不寫檔，直接交對話內關係圖或結構化對照，並說明因此未做的渲染檢查。

## 2. 圖形不能超過證據上限

- **圖題、轉折點與各格同一個確定程度：** 圖與正文用同一套證據；某事在正文或圖中任一格標「未知」，圖題與轉折點就不能把它寫成定論（「Kevin 上台報告」只能畫成報告，不能寫成「處長看到的作者是 Kevin」）。
- **圖與正文共用 [SKILL.md 的鐵律](../SKILL.md#2-三條鐵律)：** 文件紀錄、使用者轉述與推測以圖例或簡短標註區分，不必每個詞重複貼標籤。書中案例類比用註解連到判斷，不畫成本案已發生的事實。
- **分清不同性質的連線：** 正式匯報、實質影響力、依賴、日常寄信／抄送（CC）路徑、與衝突要分別標明——寄信給某人不等於能影響他，收到副本也不等於未參與。
- **隸屬方向不依稱謂推定：** 「主管」等未標明方向的稱謂，在文件（誰交辦誰）或使用者確認前，上下隸屬畫成未知。
- **立場與行動分清「現況」與「目標」：** 未知立場單獨標示並連到查證或條件分支，絕不放進「反對 ↔ 中立 ↔ 支持」中間猜成中立；擬議的未來行動與已發生的事分開標示。
- **硬限制與退路定義準確：** 上級定死的安排（環境固定限制）與使用者個人紅線用不同標記；獨立退路（BATNA）、仍需同一批核准者同意的縮小試點與待開發的出路分開標示，擬議行動不用已成立關係的線型。
- **貢獻對照看實質增量：** 保留版本、實際新增內容與適用範圍；視覺面積、線條粗細與顏色只表達有證據支持的差異，不捏造功勞百分比。

## 3. 版面美學與離線安全

- **設計方向：** 對話內渲染不設整頁背景、沿用環境主題變數；沿用專案或使用者既有設計方向；無指定方向時，避開米白／奶油背景、標題斜體強調、裝飾性數字段落標籤（`01/02`）、monospace 標籤與膠囊按鈕。
- **離線與資安：** 獨立 HTML 僅用內嵌 CSS、SVG、表格與必要的本機互動腳本，零遠端字型／CDN／外連追蹤。引用信件與文件文字須適當跳脫（Escape），不順手嵌入資料夾內其他私人檔案。

## 4. 內容與雙寬度視覺驗收

- **續作局部更新：** 轉折點、拍板者或主結構變了，才以既有圖為底重畫並重新預覽：只改新事實影響的標註、連線與行動，未受影響的權限、目標與退路保留原位，不藉續作重排整張圖。其他變動不重畫，在正文用一行寫明圖裡哪幾格改成什麼。不論重不重畫，沿用的格都要對過本輪使用者原話（接觸性質、誰說了什麼、時間），對不上的就列進要改的格。
- **換案測試（判斷檢驗）：** 遮住文字回覆只看圖，要答得出誰拍板、卡在哪、第一步做什麼；把人名換成別的案子還能照用，就重做，改畫只屬於這局的主結構。常見失敗：流程方塊加箭頭重述使用者計畫；所有人畫成同大小方塊、看不出權力差；證據標籤只放註腳。另沿重要連線核對人物、方向、權限、利益、依賴與來源，確認圖與推薦路徑一致；沒標的格逐格指回使用者原話，指不回的補「推測」或「未知」。
- **先確認可用的預覽方式：** 開啟預覽前先讀工具文件，選擇受支援的本機路徑；例如只支援 HTTP(S) 的瀏覽器，可在允許臨時建檔時使用僅綁定 loopback 的本機 HTTP 預覽。一般載入錯誤先診斷原因，確實無可用方式才交受阻替代；若工具明確以安全政策或權限拒絕，遵守拒絕範圍，不換協定或工具繞過。明確禁建檔時遵守限制，私人資料不送外部繪圖服務。
- **視覺實看：** 環境有 `html_preview` 時，以 `width=375` 預覽並實際看截圖；檢查長姓名與標籤是否截斷、線條與箭頭是否重疊、有無隱藏水平溢出，修正後重看受影響部分。手機版應重排或拆視圖，不把整張桌面圖硬縮；關鍵資訊不只靠顏色或滑鼠懸停（Hover）。
- **誠實交代驗收範圍：** 正常完成時不在回覆裡敘述製作過程；受阻或未完成的項目仍簡述原因與影響。檔案存在、Mermaid 原碼或結構檢查只算製作狀態，**實際渲染觀看才算完成視覺驗收**；若工具、權限或「不建檔」限制使渲染預覽受阻，當回合直接交出可讀的對話關係圖或文字對照，並明確列出受阻原因與未驗證的視覺項目。

# 分支：借調單上有沒有寫結束日

卡點：關鍵事實未知｜圖型：分支｜交付：判讀輪＋精簡圖｜成品：[branch-secondment-end-date.html](branch-secondment-end-date.html)

## 情境

資料工程師三個月前被借調去支援會員 App 改版。原部門組長要他月底回去接年度報表，專案經理說上線前誰都不准走，兩人都叫他自己去跟對方講。借調單是他自己填的，結束日那欄有沒有寫，只有他翻得到。

## 使用者原話

> 我三個月前被借調去支援會員 App 改版，原本的組長佩珊說月底要我回去接年度報表，專案經理承翰說上線前誰都不准走，兩個人都叫我自己去跟對方講。我在專案這邊還有兩支 API 沒交接。當初借調單是我自己填的，結束日那欄我不記得有沒有寫。我要先找誰談？

## 錯誤示範

畫成「佩珊 ← 你 → 承翰」的拉扯圖，兩條箭頭各寫一句對方的要求。失敗類型：人物關係圖。換成任何夾在兩個主管中間的人都能套，看得出誰在拉你，選不出第一步。

## 對的答案骨架

1. 判斷和第一步：卡在借調單有沒有寫結束日，不在先找誰；不要分開找，兩位主管放在同一封信。
2. 同一輪就問：「借調單結束日那欄有寫嗎？寫哪天？」有寫就附借調單，沒寫就附你擬的回組日期和交接清單。
3. 先交不用等答案的話：「兩邊的事我都想收好尾，回組日期想請兩位一起定。我手上還沒交接的是兩支 API。」

## 依據

- 機制：《Getting to Yes》客觀標準。兩位主管各有立場時，拿雙方本來就認的文件當準，不比誰比較大聲。借調單有寫結束日，就走這條。
- 故事：getting-to-yes-094〈主管調解兩名部屬的不同方案〉。書中主管不在兩個方案之間來回折衷，而是自己擬一份草案，請兩方挑毛病再改。本案差在你不是主管，是被爭的那個人；但書中也說當事人可以替自己的爭議當調解者。所以借調單沒寫日期時，選「自己擬草案給兩位一起改」，不選「分別去說服兩位」。

## 這張圖改變了哪個決定

使用者原本在想「先找佩珊還是承翰」；圖把問題換成「借調單有沒有寫結束日」，第一步改成兩位放同一封信，信裡附什麼由這個事實決定。

## 換案測試與規格

圖裡的借調單、結束日欄位和兩支 API 的交接都來自這段原話。換成另一個夾在兩位主管之間、但沒有借調單的人，這張分支就不成立。精簡圖：3 個節點（一個待問的事實、兩支第一步），每個節點連同「有寫／沒寫」最多 19 字（不算空白、標點與證據標籤）。兩支的第一步都是今天就能寄的信，沒有一支要先等別人回覆。

## 為什麼不用別的圖

決策圈會去排誰官大、誰能拍板；本案要先知道的是借調單寫了什麼，這個答案一出來，誰的要求站得住就跟著定了。
